1. INTRODUCTION                                            *meatcode-intro*

Browse the NeetCode roadmap and the merged LeetCode/NeetCode/LintCode catalog,
solve problems in real buffers, run matching NeetCode visible cases locally,
and submit through the first provider in the submit chain that can open them.

Local runs resolve a stage-major oracle chain: an openleetcode checker,
provider reference solutions, official editorials, sanity-checked popular
community solutions, then the cloud — the submit judge's own test run,
checked against cached answers first. The provider chain breaks ties inside
each stage.

Requires Neovim 0.10+, `curl`, and telescope.nvim. Local runs need `python3`,
a C++ compiler, `swiftc`, or `rustc`; checkers always need `python3`.

3. AUTHENTICATION                                           *meatcode-auth*

Browsing works signed out. Submission requires an account with the selected
provider.

Run `:MeatCode login leetcode` to see how to copy the complete Cookie request
header from a signed-in leetcode.com tab. It must contain LEETCODE_SESSION and
csrftoken.

Run `:MeatCode login neetcode` to see how to extract NeetCode's Firebase refresh
token from browser storage.

Run `:MeatCode login lintcode` for a console script that prints your LintCode
refresh token from a signed-in www.lintcode.com tab; press y to copy the
script, p to paste what it prints. The plugin mints short-lived access tokens
from it, so the session survives longer than the few minutes an Authorization
header copied out of DevTools would last.

All credentials are written below `stdpath("cache")/meatcode` with mode 0600.
Use `:MeatCode logout <provider>` to remove one, or press <CR> on a status row
of the homepage to log that provider in or out.

4. COMMANDS                                             *meatcode-commands*

                                                                  *:MeatCode*
:MeatCode               Open the homepage: providers, workspace, progress, jumps.
:MeatCode home          Same as above.
:MeatCode roadmap [NAME]
                       Open the roadmap, optionally selecting blind75,
                       neetcode150, neetcode250, or allNC.
:MeatCode list [QUERY]  Fuzzy-search the merged catalog in a full-page
                       Telescope picker.
:MeatCode random        Open a random accessible unsolved problem.
:MeatCode daily         Open LeetCode's problem of the day.
:MeatCode lang [NAME]   Show or change the solution language.
                       Supported names: python, cpp, swift, rust.
:MeatCode login NAME    Log in to `leetcode`, `neetcode`, or `lintcode`.
:MeatCode logout NAME   Remove credentials for one provider.

The homepage, roadmap and finder share one tab: running any of the commands
above jumps back to it and switches what it shows there, rather than opening
another tab each time. Opening a different problem closes the open one first
(saving its code, same as `q`); reopening the open one just focuses it. At
most one problem tab exists at a time. Login/logout refreshes the homepage
immediately, and changing `:MeatCode lang` refreshes language-filtered views
and reopens the current problem in that language without discarding its work.

Problem actions use the buffer-local mappings below instead of duplicate Ex
commands. Accepted cloud submissions are counted in the selected language; an
accept on any provider counts once per calendar day, regardless of how many
submissions landed that day. The first check for a language walks each
provider's full history automatically; after that, opening the homepage,
roadmap, or finder cheaply checks for anything new via a stored cursor. Each
check notifies when it starts and when it finishes, even when nothing changed.

5. MAPPINGS                                             *meatcode-mappings*

Roadmap ~
  h j k l / arrows      Move between topics
  <CR>                  Open the selected topic (picker overlay)
  L / H                 Next / previous curated list
  ?                     Help
  q                     Close

Topic picker ~
  type                  Fuzzy-filter topic problems
  <CR>                  Open the problem
  <C-o> / o             Fuzzy-pick a provider/solution/video link
  q / <Esc>             Close
Homepage ~
  r / l / n / d         Open roadmap / finder / random / daily
  <CR>                  Open the row under the cursor; on a provider status
                        row, log that provider in or out
  q                     Close

Problem finder ~
  type                  Fuzzy-filter by number, title, slug, difficulty,
                        topic, or company
  <CR>                  Open the problem
  <C-o>                 Fuzzy-pick a provider/solution/video link

Solving ~
  <leader>nr            Run your cases against the selected oracle, or on the
                        submit judge's test run (the cloud oracle); repeating
                        it replaces the foreground local run
  <leader>ns            Submit through the submit chain's judge; this cancels
                        a foreground local run. The verdict names the provider
                        that judged it
  <leader>nR            Reset to the content provider's starter code
  <leader>no            Fuzzy-pick a provider/solution/video link
  <leader>nc            Reorder the content/submit fallback chains and choose
                        when the cloud oracle replaces local ones (<CR> on its
                        row). The provider actually serving the open problem
                        is marked with a caret, which is not always the
                        topmost one.
  <CR> or <Tab>         Statement window: toggle the hint under the cursor, or
                        follow the link under it via |vim.ui.open()|.
  q                     Close the problem (statement/results windows)

The terminal cursor is hidden while the roadmap has focus; the selected node
already shows the position. Set `ui.hide_cursor = false` to keep it.

6. LOCAL TEST RUNS                                        *meatcode-runner*

Opening a problem discovers and caches the available oracles, reporting each
statement/provider/editorial/community request as it happens. Selection is
stage-major: openleetcode checker, reference solution, official editorial,
popular community solution, then the cloud oracle. Provider fallback order
only breaks ties inside one stage, so a NeetCode reference beats a preferred
LeetCode editorial.

openleetcode (github.com/therepanic/openleetcode) publishes open test manifests
whose Python checker decides whether any output is correct for any input —
exact even when a problem accepts several answers (Longest Palindromic
Substring). Manifests are found by LeetCode slug and cached; checkers cover
function problems only and always run sandboxed in Python.

Local candidates are validated in the background as soon as the problem opens,
one at a time in that order; community candidates are ordered by LeetCode
votes or LintCode likes and need at least one known answer. Each must agree
with every known answer: statement answers and answers learned from failed
submissions. A candidate that fails is blacklisted permanently for that
problem and language, so later passes (reopening the problem, another provider
adding candidates, the checker arriving) only try candidates not yet seen. The
first survivor becomes the oracle; an executable one immediately precomputes
outputs for your current suite.

The cloud oracle is the submit judge's test run (LeetCode/NeetCode "Run",
LintCode "Test"), logged in as for submitting. It is always cautious: the test
run starts alongside your local run and is cancelled when every output matches
a cached correct answer; otherwise the judge's verdict settles every case that
did not match, so a different valid answer passes. It judges while no local
oracle is selected, for problems that cannot run locally at all (languages
other than Python/C++/Swift/Rust, SQL, unsupported signatures or reference
encodings), and when the cloud oracle setting in <leader>nc says so: complex
problems without an openleetcode checker (default; NeetCode's
`complexTestCases`), every problem, or never.
When the test run fails, cases are graded against cached answers alone and say
so; an input with no cached answer runs with expected output N/A.

Every oracle feeds one answer cache per problem under
stdpath("cache")/meatcode/known-answers/: judge answers (failed submissions,
test runs), statement answers, and the selected local oracle's outputs, which
are dropped when it is rejected. Inputs match by content with argument labels
dropped. An output passes when it matches any answer for its input. When a
failed submission discloses an answer, the local oracle is rechecked in the
background; a failure blacklists it and advances to the next candidate.

Both `function` and `class` problems run locally in Python, C++, Swift and Rust.
Swift and Rust support scalars, nested arrays/Vecs, standard ListNode/TreeNode
types, in-place mutable arguments, design methods and codec round trips.
Rust uses only rustc and its standard library; no Cargo setup or crate fetches.
Custom node definitions and unsupported signatures fall back to the judge.
Python/C++ additionally cover helper classes such as Interval and their
documented reference encodings; see doc/local-runs.md for detailed limits.

Design problems (Min Stack, LRU Cache, Trie, ...) replay their call sequence
against the selected executable class, or compare it with a known answer list.
Encode/decode pairs such as Serialize and Deserialize Binary Tree are judged by
round-tripping the input through both halves, which needs no oracle at all.

C++ builds like LeetCode's judge: -O2 with AddressSanitizer, plus
UndefinedBehaviorSanitizer and libc++ debug hardening, so an out-of-bounds
index, use-after-free, null dereference, signed overflow or invalid sort
comparator stops a local run as it would a submission. A crash is reported
against the test case that was running: its input, what went wrong, the line
of your solution and the calls that led there, what it printed last, and the
path of the full sanitizer report (crash.log).

Provider solutions and checkers are remote code. They run separately from your
solution: oracle validation, checker grading and first-time per-case output
computation are sandboxed (cached thereafter), then your code runs alone,
unsandboxed, against those answers. Default isolation denies network and
home/repository access, and every write outside the per-run scratch
directory: bubblewrap (`bwrap`) on Linux (with a private /tmp, and the host
process table hidden behind a PID namespace), Apple's `sandbox-exec` on macOS
(an allowlist: the toolchain and system libraries can be read and run; the
shared temporary directories, the terminal and services such as the
pasteboard are denied too). Missing either fails closed (without blacklisting
any candidate) and falls through to the cloud oracle.
`runner.sandbox = false` opts into running provider code with your full user
permissions. Neither is a VM: the host kernel is shared and memory/process
resources are not cgroup-limited.

Problems that cannot be reproduced locally — SQL, and anything encoding
arguments by reference such as clone-graph's adjacency list — run entirely on
the submit judge's test run. C++ additionally cannot take vector<Interval>,
which Python handles.

Use <leader>nt to add/remove local cases in an editor. Save with :w and close
with :q. Solution edits are autosaved as you type, so switching languages,
closing the problem, or exiting Neovim preserves work without a save prompt.
Local runs also save pending edits. The full suite is stored beside your
solution as <solution-file>.cases, initially seeded with visible cases and
legacy .tests extras. An empty suite runs no cases; delete the .cases file to
restore the defaults. Changes affect local runs only.

Use <leader>na to add and save the latest failed submission input. Duplicate
inputs are skipped; a disclosed expected output joins the answer cache.

Legacy extra test cases can be added in a file next to your solution named
`<solution-file>.tests`, with cases separated by a line containing `---`: >

    nums=[1,2,3,4]
    target=7
    ---
    nums=[0,0]
    target=0
<

Independent cases run concurrently in separate processes and are merged back
into case order. `runner.parallelism = 0` uses up to the CPU count, `1` is
sequential, and N caps workers at N. The selected oracle is cached by source
hash plus known-answer fingerprint and the blacklist by source hash, so
reopening a problem re-runs no provider code. Editing the local suite does not
invalidate either; a judge-learned answer rechecks the selection.

7. CONFIGURATION                                           *meatcode-config*

Defaults: >lua
    {
      list = "neetcode150",
      lang = "python",
      solutions_dir = vim.fn.stdpath("data") .. "/meatcode/solutions",
      cache_dir = vim.fn.stdpath("cache") .. "/meatcode",
      catalog_max_age = 24 * 60 * 60,
      timeout = 30,
      runner = {
        sandbox = true,
        parallelism = 0,
        python = { cmd = { "python3" }, auto_imports = true },
        cpp = {
          cmd = {
            "c++", "-std=c++23", "-O2", "-g",
            "-fsanitize=address,undefined", "-fno-omit-frame-pointer",
            "-D_LIBCPP_HARDENING_MODE=_LIBCPP_HARDENING_MODE_DEBUG",
            "-o", "{out}", "{source}",
          },
          clangd = true,
        },
        time_limit = 10,
      },
      ui = {
        node_width = 24,
        border = "rounded",
        hide_cursor = true,
        images = true,
        image_max_height = 18,
      },
      keys = {
        roadmap = { open = "<CR>", quit = "q", cycle_list = "L" },
        home = { roadmap = "r", list = "l", random = "n", daily = "d" },
        problem = {
          run = "<leader>nr", submit = "<leader>ns",
          tests = "<leader>nt", test_failed = "<leader>na",
          reset = "<leader>nR",
          links = "<leader>no", configure = "<leader>nc",
          quit = "q",
        },
      },
    }
<
`runner.cpp.clangd` generates a `.clangd` beside your solutions. Compile flags
(including `-std`) are taken from `runner.cpp.cmd`. It force includes
`.meatcode/prelude.h` (the standard library and `using namespace std;`) for
every file, plus a per-problem header carrying that problem's own helper types,
taken from the definition NeetCode leaves in its starter comment. The judge
supplies all of this implicitly, so without it a language server reports errors
on valid solutions. Your solution file is left exactly as NeetCode wrote it;
nothing is inserted into it.

`runner.python.auto_imports` prepends a `from typing import *` and any helper
types (`ListNode`, `TreeNode`, a problem-specific `Node`/`Interval`, ...) a
starter references but never defines, for the same reason: the judge supplies
them implicitly. Pyright/pylsp have no force-include equivalent, so the block
is inserted into the real file and stripped back out before every local run
and submission — see doc/python.md. `<leader>nR` (reset)
re-derives and re-inserts it.

Swift LSP support comes from your editor configuration. Install sourcekit-lsp
with the Swift toolchain (Xcode provides it on macOS), configure and enable
sourcekit through nvim-lspconfig. Its defaults support standalone files without
a project root. MeatCode does not configure, enable or start language servers.
No generated Swift package is needed, and solution files are unchanged.
See doc/configuration.md for a nvim-lspconfig example.

`runner.rust.rust_analyzer` (default true) writes rust-project.json beneath
solutions_dir and per-solution crate wrappers beneath .meatcode/rust/. Each Rust
solution is a separate crate; its edition and sysroot come from runner.rust.cmd.
No Cargo project or crate downloads are needed. Configure rust-analyzer normally
with rust-project.json as a root marker, and install rust-src for standard-library
completion/navigation (`rustup component add rust-src` with rustup).

Editor wrappers load the original solution as a module with a crate-local judge
prelude. Separate stable-Rust wrappers supply the same context for rustc checks.
Solution files contain only user code, with no generated imports or footer;
completion and check-on-save diagnostics target that buffer without line offsets.
Custom helper definitions are extracted from each starter's comments and
isolated by solution path.
Managed project changes reload only rust-analyzer clients rooted at solutions_dir.
A user-owned rust-project.json is preserved; add the generated wrappers to it.
Set runner.rust.rust_analyzer=false to disable generation.
See doc/configuration.md for details.

Function-style submissions to another provider load the judge's starter for
Python, C++, Swift and Rust. Compatible entry-point names are bridged only in
the submission payload; Swift argument labels are adapted too. For example,
containsDuplicate can forward to hasDuplicate without changing your Swift file.
Your local-run entry point is unchanged. Incompatible or unparseable signatures
are rejected before upload. Same-provider submissions and design-class APIs
are not rewritten. Future languages must register a submission adapter;
missing adapters fail before upload instead of silently submitting unchecked code.

Helper types are deliberately per problem rather than shared: `Node` is an
adjacency list in Clone Graph and a random pointer in Copy List with Random
Pointer, so no single definition is correct for both. Headers are written when a
problem is opened and `.clangd` is rebuilt from what exists on disk. Nothing
here reaches the judge. An existing `.clangd` the plugin did not write is left
alone only if it already matches `runner.cpp.cmd`; a stale or conflicting one
is overwritten.

`ui.images` draws problem diagrams inline through image.nvim, which needs a
terminal speaking the kitty graphics protocol; the diagram is shown on its own,
with no caption. Without it a diagram becomes a 🖼 line that <CR> opens
externally, as inline links do.

Highlight groups are defined with `default = true` and link to standard groups,
so a colorscheme can override any of them: `MeatCodeNodeDone`,
`MeatCodeNodeTodo`, `MeatCodeNodeSelected`, `MeatCodeEdge`, `MeatCodeBarFill`,
`MeatCodeBarEmpty`, `MeatCodeEasy`, `MeatCodeMedium`, `MeatCodeHard`,
`MeatCodePass`, `MeatCodeFail`, `MeatCodeWarn`.
